# 0002: SLRW byte order and record rules

Status: accepted by lead. Proposed by W4 (media). Affects only the game-input format.

PLAN §5.2 gives the SLRW layout (`"SLRW"` once, then `u8 kind | u64 pts_us
| u32 len | payload`) but not the byte order. W4 implements:

- `pts_us` and `len` are **little-endian** (what game engines on x86/ARM
  write natively; no byte swapping on the producer side).
- `kind`: 0 = end of stream (`len` must be 0), 1 = video, 2 = audio. Any
  other kind is an error.
- A video payload is exactly one frame (`--raw-video` size and pixel
  format); a wrong size is an error for pixel formats we know the size of.
- An audio payload is any whole number of interleaved sample frames.
- EOF on a record boundary ends the stream like an `end` record.
- Audio records without `--raw-audio` are ignored.

Code: `src/media/slrw.rs` (shared with `examples/slrw-gen.rs`).
